# AI-Powered Photo Retrieval Discovery Engine

## 1. Product Overview

Build an AI-powered **Photo Retrieval Discovery Engine** that analyzes large volumes of publicly available user feedback and conversations to discover, understand, organize, and prioritize the problems people face when trying to retrieve old, forgotten, or difficult-to-find photos and videos.

The goal is not to build a photo-search application itself.

The goal is to build a **research and product-discovery system** that continuously analyzes real-world user conversations and transforms unstructured feedback into:

* recurring photo-retrieval problems
* unmet user needs
* search/retrieval failure modes
* user intents and behaviors
* pain points and frustrations
* emerging problems
* potential product opportunities
* evidence supporting each opportunity
* trends over time

The system should help a product team answer:

> **"What are people struggling with when trying to find memories in their photo libraries, why are they struggling, how often does it happen, and what product opportunities could solve those problems?"**

---

# 2. Core Problem

Users often remember a photo imperfectly.

They may remember:

* approximately when it was taken
* where they were
* who might be in it
* what the occasion was
* what the object looked like
* what was happening in the photo
* a partial text fragment
* the feeling or memory associated with it

but they may not remember:

* the exact date
* the exact filename
* the exact location
* the exact person name
* the exact album
* whether the image was a screenshot, photo, downloaded image, or video
* which device captured it
* what keywords would successfully retrieve it

Traditional search systems are generally designed around information users explicitly know.

This creates a **memory-to-retrieval gap**:

> Users remember the experience or memory, while the retrieval system often expects metadata, keywords, or precise concepts.

The Discovery Engine should identify these gaps by studying what real users say.

Create a system that can ingest, process, analyze, cluster, and visualize publicly available conversations related to:

**photo search, photo retrieval, finding old photos, lost memories, forgotten photos, Google Photos search, Apple Photos search, photo organization, screenshot retrieval, video retrieval, memory retrieval, visual search, and related experiences.**

The system must transform raw conversations into structured research insights.

The output should be useful to:

* Product Managers
* UX Researchers
* Designers
* Researchers
* Search/Relevance teams
* AI/ML teams
* Photo-storage/product teams

# 9. Data Cleaning

Before AI analysis, normalize the dataset.

The cleaning pipeline should:

* remove duplicate content
* detect near-duplicates
* remove obvious spam
* remove irrelevant advertisements
* normalize whitespace
* normalize encoding
* detect language
* preserve original meaning
* remove unnecessary HTML/markup
* identify quoted content
* identify automated content
* identify low-information posts
* detect potentially sensitive personal information

Do not aggressively remove conversational context.

A short sentence such as:

> "I remember everything about the photo except when it was taken."

may contain extremely valuable research information.

# 10. Conversation Understanding

Do not treat each piece of text simply as a "review."

The system must determine the **user's underlying retrieval problem**.

For every relevant conversation, identify:

### A. User intent

Examples:

* find a specific photo
* find a specific video
* find a screenshot
* find photos of a person
* find photos from an event
* find photos from a trip
* find photos from a particular period
* find something based on visual appearance
* find something based on memory
* retrieve deleted content
* retrieve archived content
* locate downloaded images
* locate documents
* locate memes
* locate receipts
* locate childhood photos
* locate old family memories

### B. Retrieval strategy

Determine how the user attempted to find the item.

Examples:

* date search
* location search
* person search
* object search
* keyword search
* natural-language description
* album search
* scrolling manually
* visual similarity
* OCR/text search
* filename
* device
* folder
* memory-based query

### C. Failure reason

Examples:

* user doesn't know the exact date
* user doesn't remember the exact location
* search doesn't understand natural language
* synonym mismatch
* object not recognized
* person not recognized
* text not detected
* OCR failure
* visually similar objects confused
* video difficult to find
* screenshot not indexed correctly
* deleted/archived item unclear
* search ranking failure
* too many irrelevant results
* correct result buried
* user doesn't know what query to write
* search requires metadata the user doesn't remember
* search works only with literal terminology
* multiple memories are mixed together

# 11. Memory-Based Retrieval Analysis

This is the most important capability.

The system should identify situations where:

```text
WHAT USER REMEMBERS
        ≠
WHAT SEARCH SYSTEM REQUIRES
```

For example:

User says:

> "I remember a photo from a college trip where we were standing near a waterfall, but I don't remember the year."

The engine should extract:

```text
Known memory:
- event: college trip
- scene: waterfall
- people: friends
- approximate period: college years

Unknown:
- exact date
- exact location

Potential retrieval challenge:
- user has semantic/contextual memory rather than metadata memory
```

Store this as a structured **memory retrieval scenario**.

# 12. User Mental Model Extraction

The system should identify how users naturally think about memories.

For example:

### Temporal memory

"I think it was sometime around 2018."

### Spatial memory

"It was from our Goa trip."

### Social memory

"It's the photo where me and my college friends were together."

### Visual memory

"There was a red car in the background."

### Event memory

"It was the day we graduated."

### Text memory

"I remember there was a sign saying..."

### Emotional memory

"This was the photo from my first job."

### Contextual memory

"It was taken during the trip when we stayed at that resort."

These memory dimensions should become first-class data fields.

# 15. Semantic Clustering

Use embeddings/vector search to group semantically similar conversations.

Do not cluster solely using keywords.

For example, these should potentially belong to the same cluster:

> "I can't remember when I took this."

> "I have no idea what year this photo is from."

> "I know the picture but not the date."

> "I wish I could search by approximate time."

They may describe the same underlying problem:

**Retrieval when exact date is unknown.**

The UI should allow researchers to inspect the individual conversations behind each cluster.

---

# 16. Problem Discovery

The system should move beyond sentiment analysis.

The key question is:

> **What recurring problem is being expressed?**

For each discovered problem, generate:

### Problem title

Example:

**Users struggle to find memories when they remember the story but not the date.**

### Problem statement

A concise description of the underlying user difficulty.

### Evidence

Links to the conversations supporting the problem.

### Frequency

Number of relevant conversations.

### Source diversity

Number of different platforms where it appears.

### Recurrence

How consistently the problem appears over time.

### User severity

Estimated frustration/impact based on evidence.

### User segments

Examples:

* casual users
* heavy photo users
* parents
* travelers
* students
* professionals

Only infer a segment when there is sufficient evidence.

### Example queries

Show what users actually attempted.

---

# 17. Opportunity Discovery

After identifying problems, generate possible opportunity areas.

Important:

The system should distinguish:

```text
Observed problem
        ↓
Underlying user need
        ↓
Potential opportunity
        ↓
Possible solution hypothesis
```

Do not automatically assume that a generated solution is validated.

Example:

Observed problem:

> Users remember an event but not the date.

Underlying need:

> Search using approximate contextual memory.

Opportunity:

> Memory-first photo retrieval.

Possible solution hypothesis:

> Allow natural-language searches describing a remembered event and infer candidate dates, people, places, objects, and visual context.

The system should explicitly label these as **hypotheses**, not facts.

# 34. Deduplication

Duplicate detection is extremely important.

The same discussion may appear:

* reposted
* quoted
* syndicated
* cross-posted
* summarized
* referenced by another platform

Use both:

### Exact matching

For identical text.

### Semantic similarity

For paraphrases and reposts.

Maintain an indication of:

```text
original
duplicate
possible duplicate
cross-post
```

Do not accidentally inflate problem frequency because one conversation appears multiple times.

---

# 35. Source Weighting

> 1,000 App Store reviews = 1,000 independent users.

* raw volume
* unique conversation count
* source distribution
* approximate evidence diversity

The dashboard should include an **Evidence Limitations** section.

The system should discover **problems before solutions**.

Do not force every conversation into a predefined solution.

```json
{
  "query": "Why do users struggle to find photos when they don't remember the date?"
}
```

Output should contain:

```json
{
  "answer": "...",
  "evidence": [
    {
      "conversation_id": "...",
      "source": "reddit",
      "url": "...",
      "excerpt": "..."
    }
  ],
  "problems": [],
  "confidence": 0.89
}
```

Answers must be grounded in the internal research dataset.

---

# 52. Frontend UX

The visual design should feel like a modern AI research product rather than an analytics-heavy enterprise dashboard.

Prioritize:

* clean information hierarchy
* readable evidence
* fast filtering
* visual clustering
* interactive exploration
* easy navigation from insight → evidence
* minimal unnecessary decoration

The most important artifact on screen should be the **user evidence and discovered problem**.

---

# 53. Seed Dataset

Create a small seed/demo dataset so that the application works immediately after setup.

The demo dataset should simulate conversations from multiple sources and demonstrate:

* different intents
* different memory types
* different failure modes
* multiple clusters
* trends
* emerging problems
* evidence chains

Clearly label simulated data as:

**DEMO DATA**

Do not represent synthetic conversations as real user evidence.

---

# 54. Security

Implement:

* authentication
* role-based access
* protected APIs
* environment-variable based secrets
* no API keys in frontend code
* secure database access

Support at least:

```text
Admin
Researcher
Viewer
```

# 56. Future Extensibility

Architect the system so future versions can incorporate:

* browser search behavior
* anonymized product telemetry
* support tickets
* customer interviews
* survey responses
* internal research
* direct user feedback
* search-query logs
* experiment results

The same research schema should be able to combine these sources.

# 57. Final Product Goal

At the end of the build, a researcher should be able to open the application and go from:

```text
Millions of unstructured conversations
                ↓
"What are users struggling with?"
                ↓
Discovered problem
                ↓
Underlying user need
                ↓
Evidence
                ↓
User behavior
                ↓
Failure mode
                ↓
Emerging trend
                ↓
Opportunity hypothesis
```

The product should function as an **AI-powered continuous discovery engine for photo retrieval**, turning scattered user conversations into structured, evidence-backed insights that can inform future photo-search and memory-retrieval products.

---

# 58. Build Instructions for the Coding Agent

Build this as a **working full-stack web application**, not merely a prototype screen or static mockup.

The coding agent should:

1. Create the complete application architecture.
2. Implement the backend and database.
3. Implement the frontend dashboard.
4. Implement the ingestion pipeline abstraction.
5. Implement AI analysis using configurable LLM providers.
6. Implement embeddings and semantic search.
7. Implement clustering and problem discovery.
8. Implement evidence traceability.
9. Implement human review.
10. Implement trend detection.
11. Implement the research assistant.
12. Seed the application with clearly labeled demo data.
13. Add authentication and basic roles.
14. Add automated tests for critical workflows.
15. Add README and setup instructions.
16. Use environment variables for secrets.
17. Make the application runnable locally with a simple setup process.

Do not build only the UI first.

Build the underlying data model and processing pipeline so that the dashboard is connected to real structured data.

When a capability cannot be implemented because a source requires an unavailable API or permission, create the connector interface and a mock/demo implementation rather than hard-coding fake production behavior.

---

# 59. Definition of Done

The MVP is complete when a user can:

```text
1. Load/import conversation data
2. Process the data with AI
3. Search the dataset semantically
4. See identified user intents
5. See memory dimensions
6. See retrieval failure modes
7. See automatically generated problem clusters
8. Open a problem
9. Trace the problem back to evidence
10. Explore trends
11. Discover emerging problem areas
12. Ask the AI research assistant questions
13. Review/correct AI classifications
14. Generate a research brief
```

The final application should demonstrate the complete loop:

**Data → Understanding → Clustering → Problem Discovery → Evidence → Research Insight → Opportunity.**
